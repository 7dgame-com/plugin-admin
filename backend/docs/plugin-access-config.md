# 插件动态访问配置

`GET /api/v1/plugin/access-config/:id` 为主后端提供当前插件访问配置，复用现有 `plugins` 表，不新增权限表。

仅提供公共插件（`organization_name IS NULL`）的最小权限元数据，字段内容在现有公共插件列表中已经公开。不需要用户 Token，也不回调主后端验证 Token，避免同步调用占满主后端工作进程。私有组织插件不支持该接口，包括空字符串或空白组织名也不会当作公共插件。接口只提供配置，用户身份验证与业务授权全部由消费它的主后端完成。

```json
{"code":0,"message":"ok","data":{"policy_version":1,"id":"sn-management","enabled":true,"access_scope":"root-only"}}
```

每次请求直接读取数据库，响应使用 `Cache-Control: no-store`。插件不存在、停用或非公共插件时返回 404；字段缺失、配置非法、数据库不可用时返回 503，绝不把缺失配置转换成 `auth-only`。接口不返回插件 URL、组织名、完整配置或数据库凭据，也不接受调用方提交的角色作为授权依据。

SN 管理的主后端通过显式部署配置 `PLUGIN_ACCESS_CONFIG_BASE_URL` 指向同环境的系统管理服务。主后端在每次管理请求中重新读取配置并检查当前已认证账号的实时角色，不转发用户 Token。SN 默认注册为公共插件、`root-only`；root 将访问范围切换为 `admin-only` 后，root/admin 可管理；改回后，admin 的下一次管理请求被拒绝。设备 SN 会话始终不得调用管理操作。SN 所属账号仍仅限正常启用的普通账号。将 SN 设为私有组织插件时，当前配置接口拒绝返回元数据，主 API 也拒绝管理访问。

部署顺序：先更新系统管理后端，再配置及更新主 API，最后更新 SN 插件。两个主 API 必须读取同一权威配置库对应的服务。主站对已打开菜单的刷新与业务接口即时授权是两件事；即使页面尚未刷新，后端仍按最新配置拒绝未获授权的操作。
